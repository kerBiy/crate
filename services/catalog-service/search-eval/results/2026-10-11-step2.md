# ListenBrainz listener counts: endpoint before/after (2026-10-11)

Step 2 of the popularity work (docs/adr/012-listenbrainz-popularity.md): formula C, w = 2, in
`SearchRanking`, measured on the real `GET /albums/search`. This is not the offline mirror.

Method: today's code on an empty `catalog_eval`, all three sets (`step2-before-*.json`); then the new code,
again on an empty database (`step2-after-*.json`). The runs were back to back, so MusicBrainz's index had
little time to drift. The scores below are from the cold pass (MusicBrainz and ListenBrainz asked); the warm
pass replays the same rankings from the cache.

**ListenBrainz in the after-run:**
- 58 calls for 64 cold searches, 0 failures. The other 6 needed no call: every result already had a
  count from an earlier query in the run.
- Call time median 65 ms, max 777 ms. The handful above 500 ms include waiting for our 1-call/s limiter
  when two cold searches came less than a second apart.
- 2325 albums stored; 1867 have a count fetched (the rest came only from the artist path, which needs none),
  and 1392 have more than 0 listeners.

**Cold latency (median):**
- main: 2092 → 2050 ms
- held-out: 1960 → 2053 ms
- niche: 1045 → 2001 ms. A niche-only rerun on an empty DB gave 1039 ms with the same ranks, so the 2001 was
  MusicBrainz being slow during that run. ListenBrainz took 56–225 ms per call in that rerun.

Warm searches stay at ~12 ms (cache replay, no ListenBrainz call).

**Found during the run:** the first after-run got `400 Bad Request` from ListenBrainz on every call. Spring's JDK
request factory streams a POST body chunked, and ListenBrainz rejects chunked bodies (curl confirms it:
the same body is 200 with Content-Length, 400 with `Transfer-Encoding: chunked`). The fallback worked as
designed: every search ranked as before, and none failed. The client now buffers the body, and
`ListenBrainzClientTest` asserts a Content-Length and no Transfer-Encoding (it fails without the fix). The
numbers above are from the rerun after the fix.
